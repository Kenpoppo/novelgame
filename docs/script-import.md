# 台本の自動読み込み(AI解析)

`/editor/import`(メイン画面の「📥 台本を読み込む」タイル)、または
`/start`(オンボーディングウィザードの「既存の台本を使う」)から、既存の
台本テキストを貼り付ける/ファイルを選ぶと、キャラクターとセリフを自動で
検出し、プロジェクトに反映できる機能。

解析ロジック本体は `app/composables/useScriptImportAnalysis.ts` に集約
されており、`/editor/import.vue` と `/start.vue` の両方がこれを呼ぶ
(過去に2画面へ別々に実装されており、一方の修正がもう一方に反映されず
不具合が再発した経緯があるため統合した。詳細は
[decisions.md](./decisions.md)の2026-08-17のエントリを参照)。

## 解析の優先順位

`useScriptImportAnalysis()` の `analyze()` は3段階でフォールバックする。

1. **自前のテキストDSL**([script-format.md](./script-format.md))として
   `parseScript()` でパースを試みる。`@char` で登録されたキャラクターの
   発言が2件以上あれば、この結果をそのまま使う(最も高精度)。
2. **AI解析** — `POST /api/import/analyze` を呼ぶ。`ANTHROPIC_API_KEY` が
   設定されていれば Claude(`claude-opus-5`)に台本テキストを渡し、
   タイトル案・キャラクター(名前+配色案)・セリフ/地の文のビート列を
   構造化出力(`output_config.format` + Zodスキーマ、
   `@anthropic-ai/sdk/helpers/zod` の `zodOutputFormat()` +
   `client.messages.parse()`)として抽出する。
3. **ヒューリスティック解析** — AIが使えない(`ANTHROPIC_API_KEY` 未設定)、
   または失敗した場合、`analyzeScriptHeuristically()`
   (`shared/domain/project/heuristicAnalyzer.ts`、`scriptImport.ts`から
   再エクスポート)にフォールバックする。台本をアップロードする人ごとに
   書式がバラバラなため、複数パターンを優先順位付きで併用する:
   1. 名前だけの行 + 次の行が「セリフ」(または『セリフ』)の2行パターン
      (実際の台本で最も多い形式)。
   2. 同一行「名前: セリフ」「名前「セリフ」」。
   3. 名前の再掲がなく「セリフ」だけが連続する行は、直前の話者の続きとして
      扱う(空行を挟んだら引き継ぎをリセット)。
   4. 敬称・役職違いの表記ゆれ(「たかし」「たかし刑事」等)を名寄せして
      1人にまとめてから、台本全体で2回以上話者として出現する名前だけを
      正式なキャラクターとして採用する(頻度フィルタ)。
   実サンプル台本での検証結果や設計判断の詳細は
   [decisions.md](./decisions.md)を参照。

どの経路の結果も `ScriptAnalysis`(`title?`, `characters: {name, color?}[]`,
`beats: {speaker: string|null, text}[]`)という共通形式に正規化してから
`analysisToProjectFragments()` で新しいidを採番した `CharacterAsset[]` /
`Beat[]` に変換する(`shared/domain/project/scriptImport.ts`)。これにより
3つの解析経路が最終的に1つの変換ロジックへ合流する。

## 「登場人物」セクションとの統合(プロフィールマージ)

台本テキストの中に `【登場人物】` のような見出しで始まる人物設定セクションが
含まれている場合、それを本編のセリフと混同しないよう別扱いする:

1. `extractProfileSection()` が、見出し(`【登場人物】`等)から次の見出し・
   長い区切り線・本編のセリフ(「」で始まる行)が現れる直前までを
   「プロフィールセクション」として切り出す。見出しが無ければ空文字を返し、
   プロフィール解析自体をスキップする。
2. 切り出したセクションだけを `parseProfileText()`(`profileImport.ts`)に
   渡し、名前+人物設定のブロックを抽出する。
3. `mergeProfilesIntoCharacters()` が、台本解析(DSL/AI/ヒューリスティック)
   で検出したキャラクターと、名前の完全一致・前方一致(4文字以内の差)で
   マッチングし、notes(人物設定)を補完する。マッチしなかったプロフィールは
   新規キャラクターとして追加する。
4. `removeProfileSection()` が、台本本文からプロフィールセクション
   (見出し行を含む)を取り除いたテキストを返す。DSL判定/AI解析/
   ヒューリスティック解析によるビート(セリフ・ナレーション)検出は、
   `extractProfileSection()` で切り出した元の全文ではなく、**この
   取り除いた後のテキスト**にかける。これをしないと、人物紹介の文章が
   すべてナレーションのビートとしてストーリーに混入してしまう
   (詳細設定のストーリー編集画面が人物紹介で埋まって邪魔になる、
   プレイ中に人物紹介を1行ずつ送る必要が生じる、といった問題があった)。
   `extractProfileSection()`(切り出す側)と`removeProfileSection()`
   (取り除く側)は同じ見出し・終端判定ロジック(`findProfileSectionRange()`)
   を共有しており、判定がズレることはない。

**重要**: この `extractProfileSection()` によるセクション切り出しを行わずに
台本全文をそのまま `parseProfileText()` に渡すと、本編の「名前」+「セリフ」
というセリフブロック(空行区切り)まですべて1件のプロフィールとして誤検出し、
キャラクターが数百人単位で誤検出される(実際に `/editor/import.vue` に
この処理が漏れていたことがあり、実サンプルで371人検出という不具合が
発生した。詳細は[decisions.md](./decisions.md)の2026-08-17のエントリを参照)。

「本編突入」の判定(＝どこで登場人物リストの抽出を止めるか)は、行全体が
「」(または『』)だけで構成されている場合、または「名前「セリフ」」の同一行
パターンの場合に限定している。人物紹介文の中で番組名等を「」で参照している
だけの行(例:「DJヤチの街角ヴィーナス」ディレクター。)まで本編突入と
誤判定すると、まだ続くはずの登場人物リストを途中で打ち切ってしまう
(実際にこの誤判定で16人中8人しか抽出できなかった不具合があった。
詳細は[decisions.md](./decisions.md)の2026-08-17のエントリを参照)。

`mergeProfilesIntoCharacters()` のマッチングは、完全一致を全キャラ分先に
確定させてから、前方一致(4文字差以内)を文字数差が最小のペアから確定させる
2段階方式になっている。単純な逐次マッチだと、短い名前(例:「ゆう」)が
本来別のキャラ(例:「ゆうき」)にマッチすべき候補(例:「ゆうき警部」)を
横取りしてしまう事故が起きるため。

## デバッグログ

`extractProfileSection()`・`mergeProfilesIntoCharacters()`・
`analyzeScriptHeuristically()`・`parseProfileTextWithDiagnostics()`(＝
`parseProfileText()`)・`useScriptImportAnalysis` はいずれも
`console.debug`/`console.table` でブラウザの開発者コンソールに解析の
途中経過を出力する。検出人数やnotesが想定と違う場合、コンソールを開くと:

- プロフィールセクションの抽出範囲がどこで・なぜ止まったか
- 頻度フィルタ/集団ラベル除外/名寄せで何が除外・変換されたか
- プロフィールのブロック分割で、名前候補が更新された箇所(役職見出しの
  直後に空行なしで実名が続くケース。「なぜこのキャラのnotesが空なのか」
  の主な原因になりやすい)
- 台本キャラとプロフィールのどれとどれが結びついた(結びつかなかった)か
- 最終的な内訳(台本解析キャラ数/プロフィール抽出数/統合後の人数)

が確認できる。

**キャラクター名のプロフィール名寄せ**は完全一致 → 前方一致(4文字差以内)
の順で行うが、「はるな」⊂「はるなの父」のように残りが「の」で始まる
場合は別人(関係性を表す別キャラクター)とみなしてマッチさせない
(`fuzzyNameDiff()`)。これが無いと、本人の短い名前が無関係な
「〜の父/〜の妹」等のプロフィールに誤って結びついてしまう。

## 解析結果画面での内訳表示

プレビュー画面の「解析内訳を見る」を開くと、以下が確認できる:

- 台本解析で検出したキャラクター数(セリフに現れる話者の数)
- 「登場人物」セクションが見つかったかどうか
- プロフィール解析で見つけた人物設定の数
- 台本のキャラと名前が一致して統合(notes補完)された数
- プロフィールにしかない新規追加の数

想定より人数が多い/少ない場合、この内訳を見ることで
「プロフィールセクションが見つからなかった(＝見出しが無く全文が本編扱い)」
のか「セクションは見つかったが中の人数が多すぎる」のかを切り分けられる。

## 選択肢・分岐は対象外

抽出されるのは台詞・地の文・キャラクターのみ。選択肢(`choice`)やラベル/
ジャンプは自動生成しない — 台本の分岐構造を確実に読み取る保証がないため、
誤った分岐を自動生成するより、まず直線的な会話としてインポートし、
読み込み後にストーリー編集画面で手動追加する方針にしている。

## 反映後の遷移

「この内容を反映する」を押すと、`store.project` へ
`characters`/`beats` を追加(タイトルは検出できていれば上書き)した上で
`/editor/all`(詳細設定 — キャラクター/音源/ストーリーを1画面にまとめた
一覧)へ遷移する。分析できた内容をその場で確認・修正できるようにする狙い。
複数回インポートしても、キャラクターは名寄せせず常に新規追加になる
(同名キャラクターが重複する可能性がある。v1では許容している)。

## AI解析を有効にする

`.env` に `ANTHROPIC_API_KEY` を設定する(`.env.example` 参照)。未設定でも
アプリ全体は問題なく動作し、「台本を読み込む」機能もヒューリスティック解析で
使い続けられる — Supabase未接続時と同じ「機能単位でのグレースフルデグレード」
方針([decisions.md](./decisions.md)参照)。

## サーバー側の実装

`server/api/import/analyze.post.ts` が唯一 `application`/`infrastructure`
層のportを介さず直接 `@anthropic-ai/sdk` を呼ぶ例外的なルート
(DB永続化を伴わないステートレスな解析処理のため、port抽象化の恩恵が薄いと
判断した)。`ANTHROPIC_API_KEY` はサーバー側の環境変数としてのみ読み、
クライアントに渡さない。
