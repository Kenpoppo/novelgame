# 設計判断ログ

で残す。実装を変えた/方針を変えたタイミングで一番上に追記していく。

新しいエントリのテンプレート:

```markdown
## YYYY-MM-DD タイトル

- 決定: 何を決めたか
- 理由: なぜそうしたか
- 代替案: 検討したが採らなかった案(あれば)
```

## 2026-08-17 台本ヒューリスティック解析で「心の声」と「複数キャラ同時発話」を検出

- 決定: `heuristicAnalyzer.ts` に以下2つのパターン検出を追加した。
  1. **心の声(独白)** — 全角/半角括弧で1行にまとまった `（〜）` `(〜)` を、
     直前の名前行(または話者引き継ぎ)の本人のセリフとして取り込む。従来は
     `「〜」` だけが発話として認識され、`（心の声）` は地の文(ナレーション)
     として扱われていたため、本人のTTS音声で読み上げられず、ナレーション
     設定で読み上げられていた(またはナレーションOFF時は無音)。
     `consumeThoughtFrom()` を追加し、`consumeSpeechFrom()` で `「〜」` の後に
     `（〜）` もフォールバック候補として試すようにした。
     表示上「地の文」と区別しやすいよう、`「〜」`は括弧を剥がすが `（〜）` は
     括弧を残したままセリフ本文にする(独白マーカーとして視認できるように)。
  2. **複数キャラ同時発話** — 「しゅうへい、なつみ」のように `、,・&＆` で
     並べた行の次の非空行が発話(「〜」または（〜）)なら、指定された全員の
     セリフとして同じテキストのビートを人数分並べて出力する(データモデルが
     単一話者のdialogueビートしか持たないため、実装上は「順番に読み上げる
     N個のビート」で近似する)。`extractMultipleSpeakers()` を追加。
     複数名の後は誰の続きかが曖昧なので `lastSpeaker = null` にし、次以降の
     セリフを自動で引き継がせない(意図しない発話者に紐づくのを防ぐ)。
- 理由: 実サンプル(「名探偵しゅうへい」等)では心の声(独白)が頻出するが、
  従来は本人のTTS/ボイスで読み上げられず、ユーザー体験が損なわれていた。
  また同じ物語で複数キャラの合唱(「〜、〜/（絶対いらない…）」のような
  同時反応)も出現するため、両方まとめて対応した。
- 代替案: 複数キャラ発話を「N人の名前を連結した1人の仮想キャラクター」として
  扱う案(例: `しゅうへい&なつみ`)も検討したが、実在しないキャラクターが
  ロスターに登録され続けるのが不自然と判断し、順番にN個のビートを並べる
  方式にした(表示・TTSは各本人のものが個別に使われる)。

## 2026-08-17 プレイ画面に停止/再開機能と再生速度プリセット(1.0x/1.5x/2.0x)を追加

- 決定: `ScriptVM` に `getState()` / `restore()` を新設し、`usePlayback` から
  `onProgress` コールバック・`resume` / `getSaveState` を公開した。
  `StagePlayer.vue` は `saveKey` プロップを受け取り、dialogue に到達するたびに
  `localStorage` (キー `novelgame:play-save:{saveKey}`) へ実行位置(pointer +
  history)を自動保存する。`TitleScreen.vue` はセーブの有無に応じて
  「続きから」/「最初から」の2ボタン表示に切り替える。エンディング到達
  (`onEnd`)または復元先が命令範囲外(スクリプトが変わってオフセットがずれた
  場合)にはセーブを自動破棄する。
  - あわせて一時停止パネルの「読み上げ速度」スライダーを「再生速度」に統合
    (ボイスファイルの `<audio>.playbackRate` にも反映するように変更)、
    ワンタップの `1.0x` / `1.5x` / `2.0x` プリセットボタンを追加した。
    スライダーは従来 TTS 有効時のみ表示だったが、ボイスファイル再生にも
    効くため常時表示に変更。
- 理由: ユーザーからの要望(「プレイ中の停止・再開、メニュー画面から再度
  途中から再生できるようにしたい」「1.5倍速・2倍速機能もつけたい」)。
  タブを閉じたり編集画面へ戻った後にも、直前のセリフから再開できるように
  する狙い。セーブスロットはローカルは `local`、公開作品は `published:{id}`
  で分離しているため、複数の公開作品を並行してプレイしても混ざらない。
- 補足: 「明示的なセーブボタン」は用意していない。全てのセリフ到達で
  自動保存するため、ユーザーがいつどこで離脱してもその直前の1行から
  再開できるという設計方針。

## 2026-08-17 プレイ中、ボイス再生終了で自動的に次のセリフへ進む機能(オンオフ可能)

- 決定: `usePlayback.ts` に、ボイス(アップロード済みボイスファイル、または
  TTS)の再生が終わったタイミングで自動的に `advance()` を呼ぶ
  `autoAdvanceOnVoiceEnd` トグルを追加した。一時停止パネル(`StagePlayer.vue`)
  に「🔊 読み上げが終わったら自動で次へ進む」チェックボックスとして表示する
  (既定オフ)。
  - ボイスファイル(`<audio>` の `ended`/`error` イベント)・TTS
    (`TtsService.speak()` が返すPromise、`WebSpeechTts`/`VoicevoxTts`
    どちらも再生完了で解決する)の両方に対応。
  - `stopVoice()` を呼ぶたび(次のセリフへ進む/戻るたび)に増分する
    「世代」カウンタ(`voiceGeneration`)を導入し、完了通知が来た時点の
    世代が最新でなければ無視するようにした。これが無いと、次のセリフに
    進んだ後にキャンセルされた古いTTSの完了通知が遅れて届いた場合、
    誤ってもう一度 `advance()` してしまう(1つ余分に読み飛ばす)事故が
    起こりうる。
  - ボイスが全く再生されないビート(ボイスファイル無し、TTS無効、
    ナレーションでnarrateNarration=false等)では、このトグルがオンでも
    自動では進まない(従来通り手動で進める)。「ボイス再生の終了」を
    トリガーにする機能であり、無音時間で自動的に進めるタイマー機能では
    ないため、意図的にスコープ外としている。
- 理由: 読み上げを聞きながらハンズフリーでプレイしたいという要望。

## 2026-08-17 ストーリー編集: ビートとビートの間に直接挿入できるように

- 決定: `StoryPanel.vue` の各ビートの直前に、薄い区切り線+小さな「+」
  ボタンの挿入スロットを追加した。押すと台詞/ラベル/ジャンプ/選択肢/
  BGM/SE/背景を選べる小さなメニューが開き、選ぶとその位置(選んだビートの
  直前)に新規ビートが挿入される。既存の `addBeat()` に `atIndex` 省略可能
  引数を追加し(省略時は従来通り末尾に追加)、末尾の追加ツールバーと同じ
  ロジックを再利用している。
- 理由: 数百ビート規模の台本では、末尾に追加してから▲▼/⇈⇊ボタンや
  ドラッグ&ドロップで目的の位置まで動かすのが非常に手間だった
  (実サンプルで500〜600ビート規模のストーリーを扱っているため)。
  ビートの間に直接1つ差し込める導線を用意することで、この手間を無くした。

## 2026-08-17 セリフ末尾に地の文が続く行(「〜」　バッ 等)で複数ビートが結合される不具合を修正

- 決定: ストーリー編集画面で、無関係な複数のビート(地の文+別キャラの名前+
  別キャラのセリフ)が1つのビートに結合されてしまう不具合を精査・修正した。
  - 原因: `heuristicAnalyzer.ts` の `consumeQuoteFrom()`
    (「」の開始行から閉じるまでを1つのセリフとして取り出す関数)が、
    「単一行で完結しているか」の判定に、行末が厳密に閉じ記号で終わる
    ケースしか対応していなかった。実サンプルには
    `「ほう…それって…」　バッ` のように、閉じ記号の後に「バッ」等の
    擬音・ト書きが続く行があり、これが「まだ閉じていない複数行の
    セリフ」と誤認された。結果、次に閉じ記号が現れる行(=無関係な
    別キャラの別のセリフ)まで、間の地の文・キャラ名を含めてすべて
    1つのビートに結合されてしまっていた。
  - 修正: 開始行の中に閉じ記号があるかどうかを非貪欲マッチ
    (`/^[「『](.*?)[」』]/`)で先にチェックし、あればその行だけで
    完結しているとみなす(閉じ記号より後ろのト書き等は取り込まない)
    ように変更した。複数行にまたがる本当のケース(行末までに閉じ記号が
    無い)だけが、従来通り次の行以降を結合する処理に進む。
  - 検証: 実サンプルの該当箇所が
    `[タクシー運転手]「ほう…それって…」` / `[地の文]変装を解く` /
    `[けんじ]「はるなさんのお父さんのことですか？」` / `[ゆう]「！！！？」`
    という4つの正しいビートに分かれることを確認した。
- 理由: 台本には「セリフ」の直後に短いト書き・擬音が同じ行に書かれる
  記法が珍しくないため、行末=閉じ記号という前提は崩れやすい。

## 2026-08-17 台本読み込み時、登場人物紹介セクションをストーリーのビートから除外

- 決定: 台本テキストに `【登場人物】` 等の人物紹介セクションが含まれる場合、
  そこで検出した内容はキャラクターの `notes`(人物設定)としてのみ取り込み、
  ストーリーのビート(セリフ・ナレーション)には含めないようにした。
  `shared/domain/project/scriptImport.ts` に `removeProfileSection()` を
  新設し、`useScriptImportAnalysis` でのビート検出(DSL判定/AI解析/
  ヒューリスティック解析)は、`extractProfileSection()` で切り出した元の
  全文ではなく `removeProfileSection()` で人物紹介を取り除いた後の
  テキストにかけるようにした。
  - `extractProfileSection()`(セクションを切り出す)と
    `removeProfileSection()`(セクションを取り除く)は、見出し・終端の
    判定ロジックを `findProfileSectionRange()` として共通化し、
    2つの関数で判定がズレないようにした。
- 理由: 従来は台本全文(人物紹介込み)をそのままビート検出にかけていたため、
  人物紹介の文章がすべて地の文(ナレーション)のビートとしてストーリーに
  取り込まれていた。詳細設定のストーリー編集画面が人物紹介の文章で埋まって
  邪魔になる、実際のプレイ中に人物紹介を1行ずつ送る必要が生じる、という
  指摘を受けて対応した。

## 2026-08-17 「DJヤチ」のnotesが自動入力されない不具合を精査・修正

- 決定: キャラクター編集画面で「DJヤチ」に人物設定(notes)が自動入力
  されない不具合を精査した。原因は `profileImport.ts` の
  ブロック分割ロジックにあった。実サンプルの登場人物セクションには
  「ラジオパーソナリティ」(役職の見出し)の直後に空行を挟まず
  「DJヤチ」(本当の名前)が続く記法があり、旧実装は各ブロックの
  「1行目だけ」を名前として確定させていたため、2行目以降(本当の名前
  「DJヤチ」を含む)がすべて1行目「ラジオパーソナリティ」の notes として
  吸収され、かつ「ラジオパーソナリティ」自体が `NON_CHARACTER_TERMS`
  (個人名として扱わない語)に含まれるため、ブロックごと(=DJヤチの
  プロフィールごと)捨てられていた。
  - 修正: ブロック内で、まだ説明文(notes)が始まっていない間に別の
    「句読点を含まない短い行」が現れたら、名前候補をその行で更新する
    (最後に現れた素の名前らしい行を採用する)ようにした
    (`BARE_NAME_CANDIDATE`)。同じ原因で `ゆうと局長`・`はるなの父` も
    それぞれ「ラジオ局→職員→ゆうと局長」「その他→はるなの父」の
    連鎖で失われていたことが分かり、あわせて救えるようになった。
  - この修正の副作用として、`mergeProfilesIntoCharacters()`の前方一致
    マッチングで新たな誤マッチが発生した:「はるな」(台本側、本人)が
    文字数差の小ささだけを理由に「はるなの父」(別人のプロフィール)に
    マッチしてしまっていた。前方一致の判定に `fuzzyNameDiff()` を導入し、
    残りの接尾辞が「の」で始まる場合(「〜の父」「〜の妹」等、関係性を
    表す別キャラクター名のパターン)は同一人物とみなさないよう除外した。
  - `parseProfileTextWithDiagnostics()` に、ブロック数/採用数/スキップ数
    とスキップ理由の内訳、名前候補の更新をコンソールに出す
    `console.debug` を追加した。
- 理由: 台本によって「役職見出し+空行なしで実名」という記法は珍しくない
  ため、単純な「ブロック1行目=名前」という前提は崩れやすい。デバッグ
  ログを追加したのは、この種の「なぜこのキャラのnotesが空なのか」という
  問い合わせに今後すぐ答えられるようにするため。

## 2026-08-17 「登場人物リスト16人 vs 台本読み込み12人」の乖離を精査・修正、デバッグログを追加

- 決定: 同じ物語のキャラクターなのに、`名探偵しゅうへい登場人物.txt`
  (登場人物リスト単体)を読み込むと16人検出、`名探偵しゅうへい台本.txt`
  (セリフのみ)を読み込むと12人検出、という乖離が報告された。精査した結果、
  原因は2つ重なっていることが分かった。
  1. **`extractProfileSection()` の「本編突入」判定が誤検出していた**
     (実際に影響が大きかった方の原因)。混在ファイル

     誤反応し、そこで登場人物リストの抽出を打ち切ってしまっていた
     (16人中8人しか抽出できていなかった)。「行全体がまるごと「」で
     構成されている」または「名前「セリフ」の同一行パターン」の場合だけを
     本編突入とみなすよう判定を厳格化した。
  2. **前方一致マッチングの横取り事故**。`mergeProfilesIntoCharacters()`は
     台本キャラを先頭から1件ずつ処理し、プロフィール候補を配列の先頭から
     走査して最初に条件を満たしたものを採用していたため、短い名前

     誤って結びつく事故が起きていた。完全一致を全キャラ分先に確定させる
     1st pass、残りを文字数差が最小のペアから確定させる2nd passの2段階に
     分離し、この横取りが起きないようにした。
  - 修正後、`名探偵しゅうへい (original).txt`(登場人物リスト+台本の
    混在ファイル)を読み込むと16人・正しいnotes対応で検出できることを
    実サンプルで確認した(修正前は13人、うち2人はnotesが入れ替わっていた)。
  - あわせて `extractProfileSection()` / `mergeProfilesIntoCharacters()` /
    `analyzeScriptHeuristically()` / `useScriptImportAnalysis` に
    `console.debug`/`console.table` によるデバッグログを追加した。
    抽出範囲がどこで・なぜ止まったか、頻度フィルタ/集団ラベル/名寄せで
    何が除外・変換されたか、プロフィールと台本キャラのマッチング結果
    (どのキャラがどのプロフィールと結びついたか、または結びつかなかったか)
    がブラウザの開発者コンソールで確認できる。
- 理由: 「16人 vs 12人」という乖離自体は、一部(3人: くわばらディレクター/
  ともやプロデューサー/プリけつ大魔神)は台本(セリフのみ)に一切登場しない

  バグではない。しかし残りの差分は上記2つの実装バグによるものだったため、

  名寄せ後の合算で生き残りやすくなる。

  等の誤検出が新たに増えたため不採用。頻度フィルタは常に2回以上を要求する
  ままとし、名寄せによる合算のみで単独発言キャラの取りこぼしを緩和する
  方針にした。
- 理由: AI解析(Claude API)は`ANTHROPIC_API_KEY`が必要でコストが発生するため、
  ユーザーは無料で完結する改善を希望した。ヒューリスティックの中で
  「同一人物が複数の表記で登場する」ことによる精度低下は、外部ライブラリを
  使わずロジックの積み上げだけで改善できる領域だったため対応した。
- 代替案: 高信頼度パターンの頻度フィルタ免除(上記の通り新たな誤検出を
  招いたため不採用)。

## 2026-08-16 ヒューリスティック台本解析を実サンプルで検証し、複数パターン対応の解析ライブラリに強化

- 決定: ユーザーが用意した実際の台本サンプル2本(`sample/`)で
  ヒューリスティック解析(`ANTHROPIC_API_KEY`未設定時にたどる経路)の精度を
  まず計測した。結果は「名前: セリフ」「名前「セリフ」」という
  同一行パターンしか検出できておらず、実サンプルの主流フォーマットである
  「名前だけの行 → 次の行に「セリフ」」という2行構成を一切拾えず、
  検出キャラ0〜6件(うち誤検出あり)・セリフ検出率ほぼ0%という結果だった。
  これを受けて、`shared/domain/project/heuristicAnalyzer.ts` を新設し、
  以下を組み合わせた解析ロジックに強化した:
  1. 名前だけの行 + 次の非空行が「セリフ」(または『セリフ』)の2行パターン
     ― 実際の台本で最も多い形式。
  2. 同一行「名前: セリフ」「名前「セリフ」」(従来通り)。
  3. 名前の再掲がなく「セリフ」だけが連続する行を、直前の話者の続きとして
     扱う(空行=段落区切りで引き継ぎをリセット)。
  4. 頻度フィルタ: 台本全体で1回しか話者候補として出現しない名前
     (見出しや章タイトルの誤検出であることが多い)は地の文へ格下げする。
  強化後、同じサンプルで検出キャラ13件(誤検出なし)・セリフ検出
  101件/405件(サンプル1/サンプル2)まで改善したことを確認した。
- 理由: 台本をアップロードする人ごとにテキストの書式は様々なため、
  単一の正規表現パターンだけでは実運用に耐えないと判明した。書式の
  バリエーションを個別パターンとして積み上げつつ、頻度フィルタで
  誤検出を自動的にふるい落とす設計にすることで、AIが使えない環境でも
  実用的な精度を狙えるようにした。
- 代替案: kuromoji等の形態素解析ライブラリの導入も検討したが、今回判明した
  失敗要因(2行構成が拾えない/同一行パターンの構造的な誤検出)には
  直接効かないため見送った。将来的に「地の文からの固有名詞抽出」等が
  必要になった場合に再検討する。
- 補足: `shared/domain/project/scriptImport.ts` からは
  `export { analyzeScriptHeuristically } from './heuristicAnalyzer'` で
  再エクスポートしており、呼び出し側(`app/pages/editor/import.vue`)の
  import パスに変更はない。

- 理由: ユーザーからの要望(「メイン画面はもっとシンプルに」「詳細な設定は
  それぞれ分離」「メイン画面からボタンでそれぞれ設定画面に行く感じ」)。
- 代替案: モーダル/タブ切り替えでの分離も検討したが、URLが別れて
  ブラウザバック・直接リンクが自然に効くページ分割を採用。
- 補足: `CharacterPanel.vue`/`AudioPanel.vue`/`StoryPanel.vue` 自体は
  無変更(各設定ページに1つずつ配置するだけ)。状態は `useProjectStore()`
  (Pinia)がページをまたいで共有するため、画面遷移してもデータやオート
  セーブの挙動は変わらない。
- 対処: サブルート追加に伴い、`@nuxtjs/supabase` の
  `redirectOptions.exclude` に `/editor/**` が抜けていて
  `/editor/characters` 等が未ログイン時に `/login` へリダイレクトされる
  不具合が再発した(2026-08-16の「Nuxt移行時にハマった3点の対処」で
  一度直したのと同種のパターン)。`exclude` に `'/editor'`(完全一致)と
  `'/editor/**'`(サブルート、末尾スラッシュ必須)の両方を列挙する必要が
  ある点をコード側にもコメントで残した。

## 2026-08-16 UIデザインを「ポップ・任天堂ゲーム風」に刷新

- 決定: エディタ/プレイヤー/ギャラリー/ログインの全画面を、ダーク基調から
  明るくビビッドな配色 + 太い縁取り + 立体的な(押すと沈む)ボタンの
  「ポップ」なデザインへ変更した。フォントはGoogle Fonts
  「M PLUS Rounded 1c」(丸ゴシック)を採用。
  - トークンは `app/assets/css/main.css` の `:root` に集約
    (`--pop-red`/`--pop-blue`/`--pop-yellow`/`--pop-green`/`--pop-purple`
    等の塗り色 + `--pop-ink` の縁取り色)。
  - ボタンは `box-shadow: 0 Npx 0 <濃い色>` + `:hover`で浮く/
    `:active`で沈む(shadowを減らしてtranslateY)という定番の「3Dボタン」
    表現に統一(`.choice-button`/`.start-button`/`.play-button`/
    `.publish-button`/フォーム送信ボタン等)。
  - ビートの種類ごとの色分け(`.beat-dialogue`/`.beat-label`等)はダーク版の
    左ボーダーのみから、カード全体の縁取り色に変更してより視認しやすくした。
- 理由: ユーザーからの要望(「もっとポップに」「任天堂ゲームみたいな
  デザイン」)。
- 補足: HTML構造・Vueコンポーネントのロジックは変更していない
  (`app/assets/css/{main,player,editor}.css` のみの変更)。フォント読み込みは
  `nuxt.config.ts` の `app.head.link` で Google Fonts を参照。

## 2026-08-16 Nuxt移行時にハマった3点の対処

- 決定/対処1: `IndexedDB` に Vue の reactive Proxy(`store.project` 等)を
  そのまま `.put()` すると `DataCloneError: ... could not be cloned` で
  保存が失敗する(エラーはスローされるが `await` していない箇所もあり、
  UI上は気づかず「保存されたはずのキャラ/音源がリロードで消える」という
  形で症状が出た)。`infrastructure/local/indexedDbProjectRepository.ts` の
  保存系メソッドで `JSON.parse(JSON.stringify(value))` によりプレーン
  オブジェクトへ変換してから保存するよう修正(`toPlain()`)。
  Playwrightでの自動テストで「リロード後にキャラ数が増えていない」ことから発覚。
- 決定/対処2: `@nuxtjs/supabase` の `redirectOptions.exclude` はワイルドカード
  `*` を `.*` に置換した正規表現の完全一致(`^pattern$`)でパスを判定する。
  `'/editor/**'` は `/editor/` という**トレイリングスラッシュ付きの接頭辞**を
  要求するため、ルートが厳密に `/editor`(スラッシュ無し)の場合はマッチせず、
  意図せず未ログイン時に `/login` へ強制リダイレクトされた。`'/editor'`
  (完全一致)に修正。サブルートを増やす場合は `'/editor'` と `'/editor/*'`
  の両方を列挙する必要がある。
- 決定/対処3: `StagePlayer.vue` で `.dialogue-box` と `.choice-box` の
  DOM順(vanilla版から流用)だけではクリックの奪い合いが起きる場合がある
  ([legacy-vanilla-implementation.md](./legacy-vanilla-implementation.md) 時点では
  たまたま発生しなかった)。`z-index`(`.choice-box: 2`, `.dialogue-box: 1`)
  を明示して、選択肢表示中は常に選択肢側が確実にクリックを受けるようにした。
  DOM順序だけに依存するstacking順は壊れやすいという教訓。

## 2026-08-16 Nuxt(Vue) + Supabase への全面移行(Clean Architecture化)

- 決定: 「個人が作ったゲームを他のユーザーもプレイできるように」という
  要望を受け、ブラウザ完結のvanilla TSツールから Nuxt 4(Vue 3) + Supabase
  によるWebサービスへ全面移行した。フロント/ビルド/状態管理/ルーティング/
  UI/音声/バックエンド/DB/認証/配信 を一括で見直し、推奨構成を決めた上で
  そのまま実装した(ユーザーからの指示: 比較レポートより先に実装開始)。
  詳細な技術構成表・レイヤー構成は [architecture.md](./architecture.md)。
- 理由: 複数ユーザーへの公開にはバックエンド・DB・認証が必須。あわせて
  スタック全体を棚卸しした。
- 代替案: React Router v7(旧Remix)も検討したが、フォーム主体のエディタ画面
  との相性・Vue希望を踏まえ Nuxt を採用。Firebaseも検討したが、
  「本人の作品だけ編集可・公開作品は誰でも閲覧可」という権限要件に
  Row Level Security が直接合うため Supabase(Postgres)を採用。
- 補足: 既存の `src/engine/*`・`src/editor/{types,compile,sample-project}.ts`
  はフレームワーク非依存で書かれていたため、ロジックをほぼそのまま
  `shared/domain/` に移設して再利用した(無駄にならなかった)。

## 2026-08-16 Clean Architectureの適用範囲を実用重視で調整

- 決定: `application/useCases/` は複数のport(interface)にまたがる
  オーケストレーションが実際にあるもの(`publishProject` — バリデーション+
  アセットアップロード+保存+公開フラグ更新)だけを関数化した。単純な
  「stateをrepositoryに保存するだけ」のCRUDは、Piniaストアやサーバー
  ルートから対象のport実装を直接呼ぶ形にし、意味のない素通しユースケースは
  作らなかった。
- 理由: 「タスクが要求する以上の抽象化を追加しない」という方針を優先。
  すべてを型どおりuseCase化すると、1行の処理のために1ファイルを作るだけの
  ボイラープレートになり、可読性が下がると判断した。
- 補足: `AuthProvider` port は定義したが、実装ファイルは作らなかった。
  クライアント側は `@nuxtjs/supabase` の `useSupabaseUser()` を直接使う方が
  Vueのreactivityを保てるため(portでラップすると再代入のたびに
  非リアクティブなスナップショットになってしまう)。

## 2026-08-16 ローカル編集とクラウド公開を分離した設計

- 決定: エディタでの下書き編集は常にローカル(IndexedDB)で完結させ、
  「公開する」ボタンを押した瞬間だけSupabaseへ保存・アセットアップロードする
  設計にした(`application/useCases/publishProject.ts`)。ログインしていない
  状態でもエディタ・ローカルプレビューは今まで通りフルに使える。
- 理由: Supabaseプロジェクトの作成はユーザー自身が行う必要があり(AIが
  代行できない)、その手順が済むまでアプリが使えない状態を避けたかった。
  `nuxt.config.ts` はSupabase未設定時にプレースホルダーURLへフォールバック
  し、起動自体は失敗しないようにしてある。
- 参考: セットアップ手順は [setup-supabase.md](./setup-supabase.md)。

## 2026-08-16 ストーリー作成エディタを追加(GUI方式・生DOM継続)

- 決定: タイトル・キャラクター・ストーリー・選択肢・分岐・BGM/SE を
  「ユーザーが決められる」仕組みとして、テキスト手書き拡張ではなく
  **ブラウザGUIエディタ**(`index.html` → `src/editor/`)を追加した。
  UI実装は既存方針を踏襲し、フレームワークを導入せず**生DOM/TypeScript**
  のまま(状態が変わったらセクション丸ごと re-render する既存パターンを
  踏襲)。
- 理由: ユーザーへのヒアリングで選択。テキスト手書きより非プログラマに
  やさしい。フレームワーク不導入は既存コードとの一貫性・依存追加の回避を
  優先。
- 補足: テキスト台本形式(`docs/script-format.md`)は廃止せず、上級者向け
  経路 + エディタ初回シード生成用途として残した
  (`src/editor/sample-project.ts`)。データモデル詳細は
  [editor.md](./editor.md)。

## 2026-08-16 キャラクターはユーザー提供 + 再利用ライブラリ方式

- 決定: ビルトインの既定キャラクター(イラスト)は用意しない。
  ユーザーが画像をアップロードして作成する。ただし一度作ったキャラクターは
  `characterLibrary`(IndexedDB)に保存でき、以後「ライブラリから追加」で
  他のプロジェクトにも再利用できる(「既存から提案」を実現する手段として、
  ビルトイン素材ではなくユーザー自身の過去の制作物を提案する形にした)。
- 理由: ヒアリングで確認。イラスト自動生成ツールが無いため、代替手段として
  再利用ライブラリを設計した。
- 参考: ライブラリから追加する際は `id` を振り直したコピーとして
  プロジェクトに埋め込む(プロジェクト単体を自己完結させるため)。

## 2026-08-16 BGM/SE はサイト調査 + 手動アップロードで運用(ライセンス回避)

- 決定: 実音声ファイルはリポジトリにバンドルしない。フリー素材サイトを
  調査して `docs/audio-sources.md` にシチュエーション別の探し方をまとめ、
  ユーザーが実際にダウンロードしてエディタの音源ライブラリからアップロード
  する運用にした。クレジット表記不要な DOVA-SYNDROME(BGM)/効果音ラボ(SE)
  を優先候補とした。
- 理由: ヒアリングで選択。実ファイルのライセンス確認・redistribution 可否は
  トラック単位での確認が必要で、代行してバンドルするのはリスクが高いため。
- 補足: 音源ファイル未添付でもコンパイルはエラーにならず、該当の
  BGM/SE命令は黙ってスキップされる(`compile.ts`)。これにより音源が
  揃う前でもストーリーの執筆・分岐確認を進められる。

## 2026-08-16 プロジェクトの永続化に IndexedDB を採用(localStorage不採用)

- 決定: エディタの自動保存先に `localStorage` ではなく IndexedDB を使った。
  追加パッケージは入れず生 API で実装(`src/editor/storage.ts`)。
- 理由: キャラ画像・音声ファイルを data URL で保持すると `localStorage` の
  5MB 制限にすぐ到達するため。IndexedDB ならその制約がない。
- 補足: v1 は単一プロジェクト運用(固定キー `"current"` に1件のみ保存)。
  複数プロジェクトの管理・切り替えは将来の拡張。

## 2026-08-16 再生画面にキャラクターアバターを小さく反映

- 決定: エディタでキャラクター画像をアップロードできるようにした以上、
  再生画面(`renderer.ts`)にも発言者の小さなアバター(40x40, 円形)を
  名前バッジの隣に出すようにした。位置指定や差分表示などの本格的な
  立ち絵演出は対象外のまま。
- 理由: 画像をアップロードしても再生画面に何も反映されないのは
  片手落ちと判断し、低コストな範囲で反映した。

## 2026-08-16 `hidden` 属性が CSS の `display` 指定に負ける問題への対処

- 決定: `style.css` の先頭に `[hidden] { display: none !important; }` を追加。
- 理由: `.choice-box`/`.name-box` に `display: flex`/`display: inline-block` を
  直接指定していたため、JS で `element.hidden = true` にしても
  ブラウザ既定の `[hidden] { display: none }` (UA スタイルシート)より
  作者スタイルシートの詳細度が優先され、非表示にならないバグが発生した
  (Playwright での自動プレイテストで発覚: 選択肢後の終了画面で選択肢ボタンが
  消えずに残っていた)。
- 教訓: 今後 `hidden` 属性で表示/非表示を切り替える要素に `display` を
  直接指定するときは、この既存ルールがあることを前提にしてよい。逆に
  `!important` を上書きしたい要素が出てきたら、この行の存在を思い出すこと。

## 2026-08-16 parser / vm / renderer の3層分離

- 決定: 台本のパース(`parser.ts`)、実行状態管理(`vm.ts`)、DOM描画(`renderer.ts`)
  を完全に分離。`vm.ts` は `document` 等の DOM API に一切依存しない。
- 理由: 将来 Canvas 描画やモバイル向け UI に差し替えたい場合、あるいは
  VM だけを自動テスト(ヘッドレス)したい場合に、他層を巻き込まずに済むため。
- 代替案: 1ファイルに全部書く案もあったが、選択肢分岐やラベルジャンプなど
  ロジックが増える前提だったため早期に分離した。

## 2026-08-16 選択肢表示中の誤進行をVM側でガード

- 決定: `ScriptVM.advance()` は現在の命令が `choice` の場合は何もしない。
  レンダラー側では同等のチェックをしない。
- 理由: 進行ロジックの真実は VM 一箇所に持たせたい。レンダラー側にも
  同じ判定を書くと、判定がズレたときに事故る(キーボード操作だけ選択肢を
  読み飛ばせてしまう、等)。
- 参考: Playwright での自動テストで「選択肢表示中に Space を押しても
  選択肢が消えないこと」を確認済み。
